# 公司版组队（CodeAgent 多会话协作）

v0.4.1 · 随 AI Hub 安装，适用于已启用组队的公司版 CodeAgent。

一句话：**负责人管目标、接口和验收，成员各自交付一个完整模块。** 会话之间用 Hub 的组队命令通信。所有状态都写进文件，会话压缩、换号或重启后，从进展卡和 `status` 接着做。先用好已有会话和工具，再考虑加人。

**轻量协作**：下文关于交付、阻塞和接力的做法，按当前任务需要自然采用，复用已有的消息、任务书和进展卡，不要求固定表格、消息标签或逐项打勾。同类失误反复出现、值得治理时，再考虑加局部约束。已有的审批、测试、合入和保护要求照常执行。

## 0. 先确认组队可用

- 个人账号中自行编写或修改的本技能，会同步到新号池账号和仍由 Hub 管理的号池副本；号池里自行修改过的内容保留。
- 命令位置：Hub 数据目录下的 `team\hub-team.cmd`。先读 `CLAUDE_HUB_DATA_DIR`；未设置或为空时使用 `%USERPROFILE%\.ai-hub-community`。成员开工任务若给出确切路径，优先使用该路径。
- 在 PowerShell 中先设置本次命令路径，再执行动作；后文每个动作都接在 `& $teamCommand` 后：
  ```powershell
  $hubData = $env:CLAUDE_HUB_DATA_DIR
  if ([string]::IsNullOrWhiteSpace($hubData)) {
    $hubData = Join-Path $env:USERPROFILE '.ai-hub-community'
  }
  $teamCommand = Join-Path $hubData 'team\hub-team.cmd'
  & $teamCommand status
  ```
- 可用动作只有：`status`、`accounts`、`propose`、`send`、`read`、`allow`、`restart`、`dismiss`。
- 身份由当前会话的环境变量自动提供。不要让用户复制任何令牌，不在消息、日志、文件里打印令牌，也不借用别的会话的身份。
- 先跑一次 `status`，看到团队信息或「你还不在任何团队里」才算可用；无输出、超时、报错都不算。不可用就告诉用户，改为单会话继续。只改说明、讨论方案或做只读检查时，不必招人。

## 1. 值不值得组队

- 值得：任务能拆成 2 个以上边界清楚的模块，固定输入和接口后各自推进，且单会话预计要做几个小时以上。经验上，跨夜、超过 6 小时、有 3 个以上模块时收益最明显。
- 不值得：模块强耦合、每一步都要等上一步，或单会话很快能做完。短时的独立审查，交给已有成员或另一个账号的会话即可，不必为凑人数加人。
- 判断标准：拆完后，每个成员能否只靠「任务书 + 接口约定」独立推进。不能就先把接口定清楚，或者不拆。依赖别的模块的输出时，用固定样本、参考输入或模拟依赖把它隔开。

## 2. 招人（用户批准后才建会话）

1. **看号池**：`accounts`。只读本机号池和已缓存的模型权限，不登录、不联网、不改账号设置。返回：
   - `recommendedId`：推荐账号；
   - `rows`：每个号一行，字段有 `id`、`label`、`state`、`usable`、`activeSessions`、`models`、`modelsAuthoritative`、`defaultModel`，不可用时附原因。

   选号只看 `usable=true`，同一个号上的会话越少越好。号池没有额度百分比，不要估算余量。同一账号上多开会话共享该账号的限额，只有分到不同账号才可能分摊。
2. **写计划文件**（UTF-8 JSON），再 `propose --plan-file 计划.json`：
   ```json
   {"goal":"这批人一起要完成什么",
    "members":[{"role":"分工（边界）","task":"开工任务，长的写任务书路径","title":"侧栏显示名","cwd":"工作目录","account":"号池账号 id","model":"模型"}]}
   ```
   - 计划只写上面模板里的这些字段。每人必须写 `role`、`task`。`title`、`cwd` 可选，`cwd` 必须是已存在的目录。
   - `account` 可省略，省略时用 `recommendedId`。没有可用号会直接报错。
   - `model` 可省略，省略时沿用该号的默认模型（`defaultModel`）。要指定就从该号的 `models` 清单里选。`modelsAuthoritative=true` 时清单外的模型会被拒绝。
   - 成员类型固定是 CodeAgent，`kind` 不用写。
   - 在每人的 `task` 里写一句选这个模型的理由（按第 4 节），不新增计划字段，供用户批准时判断。
3. **等用户批准**。提交后计划处于「待批准」，回复用户：「请在侧栏本会话那一行点『待批准』，可逐人修改账号和模型。」
   - 只有用户能批准，你不能代点，命令行也没有批准动作。
   - 批准时 Hub 会按号池当前状态重新校验账号和模型。不通过时，整份计划留在待批准、一个成员都不建，用户改好后再批。
   - 批准或驳回的结果会作为一条消息发给你。驳回就按意见改计划，重新提交。
4. **建成后核对**：某个成员没建成时，已建好的成员照常保留，通知里会写明原因。只为缺的那几位另交一份新计划，不要重复创建已建好的成员。计划里的账号和模型不代表已生效，成员开工后请它在第一条汇报里报出实际使用的模型。
5. 每位负责人最多 8 名成员。成员不能招人，要加人请向负责人提。

## 3. 分配任务与通信

- 分配任务：`send --to m1 --message "…"`，长内容用 `--message-file 文件`。成员空闲时送达；要打断成员正在做的事，加 `--interrupt`。
- 汇报：成员用 `send --to lead --message "结论 + 文件路径"`；不急的加 `--no-wake`，不叫醒负责人，攒满 8 条或最早一条超过 30 分钟时，负责人空闲就会收到。
- 消息优先写结论和文件路径。超过约 1800 字时，Hub 会把完整正文存成文件，通知里只有预览和原文路径；收到这种通知，执行前先读原文。大段材料仍写成文件，消息里发路径。
- 读原文：`read --id 消息编号`，返回发件人、收件人、时间、完整正文和原文路径。只有本队负责人和这条消息的收发双方能读；别人读会被拒绝，转述给第三方时把要点直接写进消息。
- 通道确认可用后，日常消息直接处理并交结果，不必逐条回「收到」。
- 成员默认只和负责人说话。确有必要时，负责人用 `allow --a m1 --b m2 --reason "原因"` 开放直连，双方的消息会抄送负责人；加 `--off` 收回。抄送只有约 160 字摘要，同一对成员的多条会合并并列出原消息编号；涉及接口、取消、阻塞的判断，用 `read --id` 读原文。
- `status`：看全队状态（运行中、空闲、休眠）、每人「最近一次终端输出在几分钟前」（`runtime.lastOutputMinAgo`）、待你处理的留言（带消息编号）、没送达的消息（`undelivered`）和计划状态。会话压缩或重启后先跑一次；分配任务前也顺手看一眼。
- 送达由 Hub 兜底：明确没写进对方输入框的消息，Hub 按 1、3、10 分钟自动重发；仍不行就自动重启该成员一次（同一成员 30 分钟内最多一次，接着原会话历史）再补送，并通知负责人，不用手动重发。例外：对方输入框里有没发出的残留文字，或清空输入框需要确认时，Hub 不自动重启（免得冲掉对方正在写的内容），1、3、10 分钟重发都失败后只通知负责人；这时负责人先看对方会话，等残留发出或清掉后再 `send`，确认没人在用再 `restart --member`。标为「可能已送达」（`unconfirmed`）的，先看对方会话再决定是否重发，避免重复执行。
- **Hub 心跳提醒**（负责人会收到）：
  - 「显示在运行中，但已 N 分钟没有任何终端输出，可能卡住」：成员运行中却 10 分钟没有输出时发出。先看一眼它的会话或产物，长时间测试、构建本来就可能没有输出；确认卡住再 `restart --member`。
  - 「已不在运行」或「已休眠且没能叫醒」，有消息送不到：用 `restart --member` 重启，重启后自动补送。
- 收尾：`dismiss --member m1` 让成员离队，会话本身保留，由用户决定是否关闭；确认成员卡住后再用 `restart --member m1` 重启。这两个动作只有负责人能用。

## 4. 角色、分工与选模型

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| 负责人（1 个） | 定基线，写总纲和接口约定，分配任务，审改动，统一合入，广播新基线，维护进展卡；对外动作（发布、推送）前先问用户 | 大块实现交给成员，避免协调被实现占满；小修可自己做 |
| 模块成员 | 负责自己模块的分析、实现、自测，提交合入请求 | 不改别人模块的文件，不直接合入，不做对外动作 |
| 审查成员（可选） | 只读审查别人的改动，结论分「必改 / 建议 / 通过」 | 只审不改 |

- **按边界拆，不按步骤拆**：每人负责一段「输入 → 输出」，并负责到底。不要把一个小改动串成设计、实现、再设计的多次交接；设计或审查意见交回模块负责人，由模块负责人整合并验收。
- **成员的自主范围**：在自己的工作副本里自行读码、加诊断、做小实验和自测，日常小步自己推进。里程碑、阻塞、完成、跨模块线索和待裁决事项向负责人汇报。公共接口、集成基线、跨成员优先级和对外请求由负责人裁决。
- **遇到卡点**：能在自主范围内解决就继续；需要别人行动时，一次说清卡在哪里、需要谁做什么、自己的建议。紧急阻塞马上说，其余待决定事项可以合并着说。
- **按任务选模型**（起步默认值，以本项目同类任务的实际表现为准，随时可调）：

  | 工作 | 起步选择 | 验收看什么 |
  |---|---|---|
  | 负责人、拆任务、协调接口 | 掌握上下文的当前会话继续做 | 任务边界、阻塞处理、返工 |
  | 新界面的布局、文案、交互 | 号池里设计和审美最强的模型 | 真实页面、操作路径、用户审美 |
  | 按既定方案实现、修错、回归 | 快的模型即可，同样负责完整模块 | 功能闭环、测试、返工 |
  | 算法、复杂定位、架构取舍 | 推理强的模型 | 推导、反例、实验或代码证据 |
  | 重要的独立审查 | 与作者不同的模型 | 可复现的问题、严重程度、验证依据 |

- **审查按风险投入**：并发、数据正确性、架构和重要发布优先请另一种模型独立审查；小改动按项目要求验证即可。审查者先看需求、代码和原始证据，再看作者的结论；有分歧用实验或测试裁决，「换了模型」本身不等于正确。
- **界面不交给弱模型独立定稿**：界面的设计由强模型完成。交给较弱或较快的模型实现时，任务里必须附设计令牌（颜色、字号、间距、圆角、阴影的 CSS 变量）和逐页样稿；验收由强模型在 1440 和 1280 两种宽度下，把真实界面截图和样稿逐页并排比对（层级、间距、对齐、各种状态、空状态、动效），不达标就打回。只核功能、不核外观，是界面验收最常见的漏洞。能由强模型直接实现的界面，优先直接实现。

## 5. 开工清单（负责人做）

任务目录 `<工作根>\YYYYMMDD-<任务>\`：

```
YYYYMMDD-总纲-<任务>-lead.md     所有成员开工先读；规则变了就改这里，并通知全员
<成员>\YYYYMMDD-任务书-<成员>.md  自包含：目的、基线、只改哪些文件、验收标准、交回格式
contract\                         接口约定：字段、单位、文件格式
<成员>\                           各自的工作目录、进展卡、worktree
```

总纲必写：
- 目标与验收标准（有数值的写容差）；
- 当前优先级写在第一行，支线标明「后台」，避免主线没人推；
- 分工表（写明每人只改哪些文件）；
- 协同规则；
- 阶段划分；
- 已拍板事项（不再请示）；
- 基线版本，以及数据和前序成果的路径。

任务书：
- 自包含：目的、基线提交号、拥有的文件、禁止改动的范围、验收标准和交回格式，并说明还有哪些成员在并行做什么。
- 用文件编辑工具写入，或用 PowerShell 单引号 here-string；写完按 UTF-8 读回一遍，确认路径和反引号完整，避免路径被 shell 当命令执行而丢失。
- 只读任务就写明只读；权限不够时报告环境问题，不靠扩大写权限绕过。

## 6. 代码与合入

- 每个成员一个 worktree 和分支，从当前基线拉出；先确认测试加载的是自己的代码。不碰主检出里别人还没提交的改动。
- 共用文件的改动要小、单独提交，冲突由负责人解决。生成出来的文件不手改，重新生成。
- 修复行为问题时，附一条「撤掉修复就会失败」的回归测试。
- 合入请求格式：`合入请求 <分支> <完整提交号> 测试:<命令与结果摘要>`。
- 负责人收到后，亲自核对 diff、测试和证据，再合入。
- 负责人批量合入：先把审过的提交拣进集成分支，一次跑完整测试；通过后前移基线，并广播新提交号。成员先跑自己模块的定向测试，负责人不为同一候选重复预跑全量；基线变了、测试失败或项目要求重验时照做。
- 正在跑的长实验固定在只读 worktree 的旧提交上，不受基线前移影响。
- 推送、发布等对外动作，只在用户同意后由负责人做。

## 7. 进展卡与接力

- 每人在自己目录维护 `YYYYMMDD-进展卡-<成员>.md`，只保留一处当前状态：
  - 顶部「给用户看」：几行白话，写已经确定的结果和影响；拿不准的集中写成一行「待核：…」，不逐句加保留语；
  - 「当前状态」：整段覆盖写，记基线提交号、在途事项、在等谁、下一步和更新时间，合计尽量控制在 1 页；
  - 流水另写日志文件，不在卡里堆历史步骤。
- 每次更新后通读一遍：「当前状态」里还留着带时间的旧段落，就合并成一段，旧的挪进日志。
- 卡只由本会话写；别的会话发现问题，发消息请负责人或卡的主人改。
- **等用户拍板的事放在最显眼处**：写进「给用户看」第一行，注明已经等了多久、用户不选时默认按哪个推荐走；超过约半天没回音，下次汇报开头再提一次。
- 里程碑、卡住、需要拍板、完成时，都更新一次并汇报负责人。交付时简要说清做了什么、验证了什么、还有什么没确认，附提交号或报告路径。消息送达、成员自报完成，都不等于验收通过。需要复盘分工时，从已有记录看等待、返工或用户介入的原因，拿不到的数据写「未测」，不用忙碌程度或消息数量代表收益。
- **换号接力**：额度剩约 10% 或收到上下文提醒时，先更新「当前状态」。新会话接手时先读它、跑 `status`，再核对原任务的提交、产物和证据。结果不明时先查现场再决定是否重做，没确认的如实说明。
- 会话被压缩或重启后：先读进展卡，再跑 `status`。

## 8. 底线与共享资源

- 所有子进程后台运行、不弹窗口；需要浏览器时用无头模式。
- 不关闭、不重启用户正在用的 Hub；验证用隔离实例，自己启动的进程按进程号清理。
- 占用多核、要跑好几分钟的整套测试或构建，由负责人错开安排，不要几个成员同时把机器占满；超时先查机器负载。
- 会争用同一个桌面程序实例的任务（如 PowerPoint 自动化），先约定由谁独占、其余排队；每人只关闭自己打开的文档。
- 资料只留在本机，不发送到外部服务。
- 删除、覆盖、推送、发布前先问用户。

## 9. 踩过的坑（防复发）

1. 建议「不取某块数据」或「跳过某个输入」前，先确认它是不是后续步骤必需的输入，而不只是诊断用；否则后面的环节会静默断掉一整夜。
2. 负责人精力被支线吃掉，主线没人推：用户定的优先级写进总纲第一行，支线明确标「后台」。
3. 换号或重启后，原来的后台任务常被显示为停止，但进程往往还活着：先按进程号查存活，再决定是否重跑。
4. 工具参数可能被残留的环境变量或默认值静默截短：验收要核「最后一步的编号」「产物条数」这类硬指标，不只看返回码。
5. 成员显示「运行中」却已空闲很久、消息积压没送达：看 `status` 里的最近输出时间和 Hub 心跳提醒判断，不只看「运行中」；送达交给 Hub 的自动重发与重启（对方输入框有残留时 Hub 只通知、不重启，按第 3 节的例外处理），不手动重复发同一条。开工回执内容具体就直接分配任务，不必多一轮确认。
6. 界面实现只核功能不核外观，交付后被评「原始、难看」：按第 4 节的界面规则，附令牌和样稿，并在两种宽度下截图逐页比对。
7. 内存紧张时，宿主可能回收后台的外壳脚本，但子进程常还活着：重任务先按进程号查存活，再决定是否重跑。
