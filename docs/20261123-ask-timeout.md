# 「问一下」卡住与队列恢复（2026-11-23）

反馈版本为 v5.6.87。原话「正在排队，前面还有一个问题」对应会话旁的 `renderer/ask-aside-ui.js`，不是底栏「问问 Hub」。两条链路分别补上保障，正常回答仍使用原来的账号、模型、上下文与权限参数。

## 原因与证据边界

- 2026-11-04 的 `1c5c31c2a` 引入「问一下」：120 秒定时器只发杀进程请求，Promise 仍依赖 `close` 事件；Windows 包装进程或继承输出管道的后代未正常关闭时，队列无法释放。缺少按题取消与服务层兜底。
- 2026-11-06 的 `676cb6c2f` 接入 Codex/DSH：服务没有将取消信号传给这两个适配器。Codex 自身超时后没有等待进程树清理；DSH 的 HTTP 旁问无法由抽屉取消。
- 最可能的触发链是 CLI 等待网络/交互而无输出，再叠加退出未收尾导致队列持续占用。现有本地扫描只有症状，没有该反馈的编号、引擎与原始 CLI 日志，不能锁定为某个模型菜单、登录或网络故障。修复针对已证实的生命周期缺口，不改用户模型或网络设置。

## 修复行为

| 入口 | 连续无输出上限 | 总时长上限 |
| --- | --- | --- |
| 问一下 · CodeAgent / Claude Code | 90 秒 | 保留 120 秒 |
| 问一下 · Codex | 90 秒 | 保留 300 秒 |
| 问一下 · DSH | 90 秒 | 保留底层 180 秒 |
| 问问 Hub（含探测引擎） | 45 秒 | 保留 60 秒 |

stdout/stderr 的新输出刷新空闲计时，持续输出仍受总时限约束。计时从实际运行开始，排队期间不消耗答题时间。超时就地提示原因，提供「重试」「取消」；运行中与排队项也可单独取消。失败与取消后自动继续已有队列，不自动重发失败问题，晚到的旧结果不会覆盖新状态。

Windows 取消先运行隐藏的 `taskkill /T /F` 清理进程树，再结束当前等待；不再只靠 `close` 事件。终止命令限时 3 秒，服务最多留 5 秒收尾，避免失去响应的适配器永远占槽。DSH 通过原有观察插件传递单次取消文件并 abort 对应 HTTP 请求，不结束主终端。

没有新增常驻进程或轮询：计时器只在单次请求期间存在，结束后清理；DSH 复用已有文件观察循环。默认成功路径的账号、模型、只读分叉、UTF-8 stdin、历史记录与三槽并发限制保留；变化集中在长时间无输出和取消/失败恢复。
